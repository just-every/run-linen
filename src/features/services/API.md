# Service operations API

`registerServiceRoutes(Hono<AppEnv>)` mounts below `/api/v1` behind platform session/CSRF. `registerServiceWebhooks` mounts separately before cookie authentication: its own timestamped HMAC authenticates monitoring. Principal and workspace come from authenticated state; ISO UTC dates and UUID record IDs. Native D1 migration `0300_services.sql` owns records, immutable event history, deduplication receipts, notification outbox and service execution fences.

Every list returns `{items: ServiceRecord[]}`. Detail returns `ServiceRecord = {id,kind,ownerId,visibility,participants,data,revision,createdAt,updatedAt}`. Visibility is `workspace|operators|restricted`. Employee incident views remove diagnostics, other employee links, private audience updates and raw recovery evidence. Mutating existing records requires `revision`; competing revisions return 409. No generic status PATCH can declare recovery or complete a change.

## Graph, incident and problem

- GET/POST `/services`; create `{name,description,businessImpact,source,observedAt,freshnessMs?,visibility?,participants?}`.
- GET/POST `/service-people`; source-owned people observations `{name,externalId,source,sourceRevision,observedAt,freshnessMs,participants?}`. This is a service relationship observation, not an HR master.
- GET `/service-graph`; POST `/service-graph/edges` `{from,to,relationship,provenance:observed|asserted|inferred,source,sourceRevision,observedAt,effectiveAt,freshnessMs,value}`. Conflicting versions remain separate; no overwrite by arrival order. Missing dependencies remain unknown; stale edge flags are explicit.
- GET/POST `/incidents`; create `{title,serviceId,impact,cohorts,cadenceMs?,followupWindowMs?,visibility?,participants?}`. GET `/incidents/:id`; GET `/incidents/candidates/:serviceId` proposes correlations only.
- POST `/incidents/:id/link` `{revision,employeeIncidentId,correction?}` validates both records through current work ACL. Employee correction never changes employee recovery.
- POST `/incidents/:id/updates` `{revision,message,recipientIds}` persists audience-bound communication and outbox; `/diagnostics` `{revision,assignee,scope,hypothesis,budget}` creates parallel read-only assignments; `/diagnostic-findings` `{revision,diagnosticId,source,finding,evidenceIds,hypothesisResult,remainingUncertainty,cost}` retains disagreements and costs.
- POST `/incidents/:id/oncall` routes current declared service rotation. `/recovery` `{revision,evidence:[{evidenceId,incidentId,serviceId,cohort,observedAt,expiresAt,verifierVersion,independent,usable,negativeChecksPassed,executionId,source}]}` admits only matching execution-owned independently verified rows through `serviceWorkPort`; client assertions are insufficient. Partial cohorts remain unresolved; parent restoration does not resolve linked work.
- POST `/incidents/:id/followup` `{revision,completeThrough,source,exposureHours,recurrenceIncidentIds,causeEvidence}` records attributed observed exposure after restoration. Report denominators include only complete declared follow-up windows.
- GET/POST `/problems`; create `{title,serviceId,incidentIds,visibility?,participants?}`. POST `/:id/known-error` `{revision,cause,evidenceIds}`, `/workarounds` `{revision,text,cohorts,contraindications,source,expiresAt}`, `/prevention` `{revision,changeId}`. Workaround lists expose stale/usable flags. Prevention implementation remains distinct from effectiveness.

## Controlled change

GET/POST `/changes`, GET/PATCH `/changes/:id`. Create exact `{title,risk,impact,services,window:{start,end},cohorts,canaryCohorts,dependencies?,implementation,compensation,emergency?,emergencyReason?,visibility?,participants?}`. Implementation and compensation use execution's `{connectionId,target,beneficiaryId,verifierConnectionId,payload}`. PATCH requires revision and invalidates all current decisions on material amendment, retaining history.

POST `/changes/:id/authorize` `{revision,reason,grantReferences:[{id,version,phase?}]}` records a business control decision, not a provider grant. POST `/dispatch` `{revision,phase:canary|rollout|compensate,idempotencyKey}` checks decision/implementation, window, dependency completion, cross-scope conflicts and service fences, persists intent, then invokes the actual execution port. POST `/verify` `{revision,invocationId}` independently reads execution evidence. Rollout requires a current verified canary; compensation can fail or remain partial. Unknown dispatch never silently retries. Actual connector/grant/probe configuration is required; no simulated provider success.

## Suppliers, lifecycle and decisions

GET/POST `/suppliers`; create `{name,services,contract,currency,cost,costPeriod,renewalAt,visibility?,participants?}`. Commands `/commitments` `{revision,outcome,dueAt,ownerId,source}`, `/handoffs` `{revision,to,summary,outstanding,source,cost}`, `/accept-handoff` `{revision,handoffId}`, `/charges` `{revision,source,invoice,amount,currency,periodStart,periodEnd}`. Commands `/observations` record `{revision,commitmentId,outcome:met|missed|unknown,source,evidence,observedAt}`; `/review-outcome` `{revision,commitmentId,evidence}` requires a different observer and labels independent human review. Unreviewed claims remain reported-met. Breaches remain accountable to recorded commitment owner; handoff is offered until the recipient accepts.

GET/POST `/software-assets`; create `{name,serviceId,assetType,externalId,source,currency,acquisitionCost,renewalAt?,observedAt,freshnessMs?,visibility?,participants?}`. Commands `/assign` `{revision,personId,workId,receipt,source}`, `/return` `{revision,receipt}`, `/transition` `{revision,state,evidence}`, `/usage` `{revision,source,observedAt,periodStart,periodEnd,activeUsers,allocatedSeats,cost,currency}`, `/charges` as supplier charges, `/reclamation` `{revision,reason,affectedPeople,evidence,estimatedSaving}`. Outstanding custody prevents disposal; reclamation savings stay hypotheses and need actual authority before effects.

GET/POST `/decisions`, GET `/decisions/:id`. Packet `{title,contextId,holderId,holderRoles,options:[{id,label,consequences}],recommendation,quote,quoteSource,terms,cohorts,impact,reversibility,deadline,uncertainty}`. Context is service/supplier/change/asset and is bound to its revision. Optional `executorId` names a current service executor; an option may bind `effect:{kind:"change",changeId,implementationRevision,phase:"release"|"compensate"}`. Selection and the due worker advance that exact change through canary, independent verification and rollout using separately current grants. Missing/revoked authority remains an accountable fulfilment exception. Commands `/choose` `{revision,optionId,reason}`, `/reject` `{revision,reason}`, `/defer` `{revision,reason,nextDueAt}`, `/amend` `{revision,optional packet fields}`. Only the current named holder with required role chooses; stale context requires amendment. No command creates execution grants. POST `/decisions/:id/advance` resumes only its declared effect. Deferred decisions remain due obligations.

## Monitoring, routing and actual delivery

GET/POST `/monitors`: `{name,serviceId,connectionId,freshnessMs,cohorts,participants?}`. Connection provider `monitoring-webhook`, encrypted secret JSON `{signingSecret}`. POST public `/webhooks/monitoring/:id`, or authenticated `/monitors/:id/events`, body `{id,serviceId,status:healthy|degraded|failed|unknown,observedAt}`. Headers `X-Linen-Timestamp` epoch seconds (within five minutes), `X-Linen-Signature` lowercase HMAC-SHA256 hex of `timestamp.rawBody`. The first valid event may activate only an inbound-unobserved connection, transactionally rechecking its revision and current integration membership and writing signed-event validation provenance. Unique event ID + digest rejects conflicting replay; old observations cannot overwrite newer ones. Signed component health never certifies usable cohort recovery.

GET/POST `/oncall-rotations`: `{serviceId,startsAt,endsAt,recipientIds}`. Workspace setting `notificationConnectionId` selects provider `notification-webhook`, config `{url,allowedHosts}`, encrypted secret JSON `{token}`. Outbound POST uses bearer authentication and immutable `Idempotency-Key`, body `{id,recipient,kind,message,...}`; accepted response `{id,deliveryId}` records submitted, not delivered. POST `/service-notifications/:id/reconcile` reads the original notification connection with id and fresh nonce; a correlated dated provider receipt may establish delivered/failed, never silence. Unknown outcomes are held for reconciliation; failed delivery stays visible. Current recipient ACL and `executionHeld` are checked before sending. No provider calls occurred during implementation.

`processDueServices(env,principal)` runs under a current active owner selected by the root scheduler. It ages monitors to unknown, opens failed-monitor incidents with event deduplication, routes on-call, persists due incident/decision/supplier notifications, and drains configured outbox. A missing integration preserves needs_configuration. GET `/service-notifications` exposes scoped states. POST `/services/process-due` is owner/operator-triggered. GET `/service-reports?start=&end=` supplies UTC range, definitions, observed costs/sources, denominator counts, pending cohorts, supplier breaches and complete-follow-up recurrence; absent cost/exposure stays unavailable.

## Trusted integration exports

`getService`, `linkIncident`, `recordVerifiedRecovery`, `changeGate`, `setChangeExecutionPort`, `setServiceWorkPort`, `processDueServices`. Registration installs the real execution `changeExecutionPort` and work/evidence `serviceWorkPort`; tests may supply fixture ports only in tests.

`restoreAdoptionRecord({env,principal},{table,row,sourceId,sourceKey})` accepts native svc_records/svc_events with current owner + execution hold; no active grants, outbox or service locks are restored. Existing owner records are never overwritten. `eraseServicePerson({env,principal},{userId,reason})` anonymizes service references/history and stops recipient delivery; anonymous record/event identities remain.

Validation: `node tests/services/run.mjs` runs bundled Worker code in workerd against actual local D1. Tests cover privacy/tenant isolation, graph staleness/conflicts, private audience rejection, untrusted/partial recovery, mistaken links, changed approval, conflicting windows, canary and incomplete compensation, supplier breaches, scoped decisions, signed monitoring/replay/staleness and real report denominators. Execution/provider calls in that suite are explicitly test fixtures; hosted/provider acceptance remains separate.

`node tests/services/integration.mjs` separately exercises the actual service/execution integration against D1 and explicit test HTTP providers: immutable payload grants, canary intent/readback, rejected partial-cohort verification, full rollout, business-choice-to-release progression, revoked grant refusal, inert native restore and domain erasure. No actual provider, production or customer messages were sent.
