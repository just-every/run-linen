# Execution API

Authenticated `/api/v1`; platform session/CSRF applies. ISO UTC times. Exports from `index.ts`: `registerExecutionRoutes`, `proposePlan`, `dispatchPlan`, `cancelOrTakeover`, `reconcileOperation`, `verifyOutcome`, `processDueExecution`; functions take `{env,principal}` then input.

GET `/plans`, `/operations`, `/authority-decisions`, `/grants`; POST `/plans` takes `{workId,revision,idempotencyKey,steps}`. Step: `{action: group.add|group.remove|license.add|license.remove,actionVersion:1,connectionId,target,beneficiaryId,grantId,grantVersion,expiresAt?,revocationGrantId?,verifierConnectionId?,cohort?}`. POST `/plans/:id/dispatch` `{expectedRevision}`. POST `/operations/:id/cancel|takeover` `{expectedRevision,reason}`; `/reconcile` `{}`; `/verify` `{verifierVersion:1}`. POST `/grants` exact bound scope, validity, conditions and principal; POST `/grants/:id/revoke` `{version}`. No client evidence admission endpoint.

Missing connector configuration preserves needs_configuration; transport uncertainty preserves unknown. Provider membership readback is effect_verified only. Usable outcome requires separately configured verifier connection and fresh authenticated positive/negative workflow responses. Due removal has a separate grant and operation, not the expired addition grant.

Controlled changes: `changeExecutionPort` implements services' port. Implementation/compensation objects require `{connectionId,target,beneficiaryId,verifierConnectionId,payload}`. Grant actions are `deployment.canary|deployment.rollout|deployment.compensate`. Immutable grant `conditions.payloadHash` must be SHA256 hex of JSON serialized `{...payload,phase,cohorts,implementationRevision}`. Connector `controlled-deployment` config is `{url,allowedHosts,targets}` and encrypted secret JSON `{token}`. POST uses immutable operation ID as Idempotency-Key, body includes action/target/beneficiary/payload. GET queries operationId,target,nonce; must respond `{operationId,target,nonce,observedAt,state:'applied'|...}`. Separate workflow probe still required for usable verified outcome.

`workspace_settings.settings_json.executionHeld === true` blocks every provider write at the immediate effect boundary, including due removal and controlled release; reconciliation reads remain possible. Restore must hold first. Import history must not create live execution grants. Explicit resume is owned by adoption after reconciliation.

Identity steps: `identity.create` target is exact UPN, beneficiaryId is authoritative person identity, payload `{displayName,mailNickname}` (no inferred email); grant conditions.payloadHash binds that payload. Generated password is encrypted only in execution_secrets, never response/audit/model context. Provider identity carries `onPremisesExtensionAttributes.extensionAttribute15=linen:<operationId>`; conflicting preexisting identity is never adopted or deleted. `identity.disable` target is exact provider user ID/UPN; `sessions.revoke` is a separate granted durable obligation with fresh signInSessionsValidFromDateTime readback. Disabling identity is not represented as session revocation. Useful account delivery/onboarding remains a separate workflow probe obligation.

Plan contexts accept `contextType: work|change|commitment|engineering` with `workId` holding the domain identity. Commitment revision and current scoped access are rechecked every effect; engineering revision means grant_version and contextSnapshot.spec binds exact persisted spec. Change snapshots bind implementationRevision and exact implementation; operational state updates do not silently invalidate unchanged implementation.

`restoreExecutionRecord(ctx,{table,row,sourceId,sourceKey})` restores native plans, held operations, attempts, receipts, independent observations and decisions under an adoption hold. New imported operations have cancel_requested=1, fence=0, lease=null; unfinished effects become unknown. Grants and secrets remain inert historical custody, never activated by import. `effect.observe` grants allow explicitly separately authorized reconciliation after original write authority expires or is revoked: POST `/operations/:id/reconcile` `{grantId,grantVersion}`. This does not confer dispatch rights or revive cancellation.

Owner setup: POST `/automation-principals` `{name,idempotencyKey}` creates a real non-interactive integration identity (no password, no deliverable email, no session). Returns `{id,name,kind:'automation',interactiveLogin:false,roles:['integration']}`; use its ID as grant principal in the same owner's exact scope review. It does not create or broaden grants. POST `/automation-principals/:id/revoke` deactivates membership, revokes its grants, cancels only unstarted operations and retains unknown started effects. Employee POST `/plans/granted` resolves this identity exclusively from the referenced persisted grants, validates current membership and exact permitted beneficiary/work, and dispatches without requester role escalation.

Identity mapping: POST `/subject-mappings` `{connectionId,localUserId,providerSubject,expectedRevision?}` is owner reviewed and independently reads Graph `users/{providerSubject}`; only exact canonical provider ID is admitted. `localUserId` may be an active platform member UUID or an authoritative `work_people.id`; stored `local_kind` and source/source_id provenance distinguish them. No name/email inference. Step/Grant `localBeneficiaryId` is separate from external `beneficiaryId`. Current connection revision and mapping ID/revision bind both. Deactivated subjects remain eligible for explicitly granted removal/disable/session-revocation, never new additions. Effect probes must echo `expectedOutcome: usable|denied` as requested, in addition to nonce/version/target/beneficiary/cohort/freshness/negativeControl/usableWorkflow.

Natural intake wiring: exported `standingIntakeExecution` implements `setStandingIntakeExecution` from intelligence. Resolve takes permitted `{workId,target,beneficiaryId:<local>,kind:access|software,expiresAt?}` and returns only an existing `{actorId,step}` or null. Grant POST accepts optional `verifierConnectionId`, stored with its current revision as immutable conditions. The resolver requires that exact active verifier, connection, mapping, action, local/external beneficiary, current issuer/actor, remaining limit and expiry/removal authority. It never selects an owner as an implicit service actor or manufactures grants.

All service writes recheck authority, current actor, fence, cancellation, restoration/coexistence hold immediately before fetch, after OAuth acquisition. Redirects use native Worker `manual`; credential-forwarding redirects are not followed and write3xx are uncertain. Due sweeps rotate last_checked_at within security priority so one failed item cannot monopolize the first page. Definitively rate-limited ordinary effects back off with a bounded attempt count; security removals retain their obligation without that ordinary cap. An unknown remote write never returns to the blind-retry queue.

Temporary additions default to an absent-target precondition: Linen does not remove preexisting standing access at expiry. Removal is persisted before the initial dispatch; when provisioning provably never started/failed/cancelled, the removal cancels without touching a preexisting entitlement. Applied cancellation may use an explicitly supplied compensationGrantId; that separate grant must still be valid and the resulting denied workflow is independently verified.
