# GitHub development context

The owner can bind an existing GitHub issue to a normal ticket, or bind production
GitHub deployments to an exact preapproved standard-change template. This release
receives events only. It does not create GitHub issues, send comments, run a
workflow or grant deployment authority. Jira, Linear and Vector remain unbuilt.
The owner-only consent policy is provisional pending ct review.

Use the authenticated API to POST `/api/v1/development-bindings` with:

- `consent: true`, a numeric `repositoryId`, and the exact `repositoryName` from GitHub.
- `kind: "issue"`, the ticket's `targetId`, and a numeric `issueNumber`; or
  `kind: "deployment"`, a template `targetId` and its approved `templateVersion`.
- A private `signingSecret` of at least 16 characters. It is encrypted at rest and
  never returned by the list or creation response.

Configure that secret on the repository's GitHub webhook, pointing to
`/api/v1/webhooks/development/{bindingId}` on the installed Linen origin. Select
issue events and issue comments for an issue binding, or deployment events for a
deployment binding. Linen checks the native `X-Hub-Signature-256` signature over
the exact body, the repository ID and name, delivery identity and a five-minute
source-time window. Send delayed events for manual review instead of changing
their original timestamps. Reused identities with changed content are refused.

Issue closure adds a private note and selects **Verify with employee**, waiting
on the requester. It does not close the ticket or establish recovery. Reopening
returns it to open; new comments enter the private conversation. HR, restricted,
pending-person, erased and terminal tickets are refused. No employee notification
or outbound provider message is generated by these events.

A deployment must have `environment: "production"` and
`production_environment: true`. Its `payload` must contain numeric
`pullRequestNumber` and `runId` values configured by the deployment workflow.
Linen records canonical GitHub links on the new standard change. These are
source-provided references, not independently discovered PR or run associations.
Each deployment identity creates at most one change per binding. The exact
current template supplies the plans and scope, with a one-hour record window
starting at the deployment timestamp; freeze and separate execution gates remain.
A deployment event does not prove successful execution or employee recovery.

GET `/api/v1/development-bindings` lists owner-visible metadata. POST
`/api/v1/development-bindings/{id}/revoke` immediately disables the binding and
clears its secret. An inactive issuing owner prevents further intake. Subject
erasure revokes affected ticket bindings. Archives carry bindings inactive and
without secrets; restored bindings cannot resume intake. There is no reactivation
door in this release. A replacement binding for an existing unique target needs a
future owner-reviewed replacement flow.
